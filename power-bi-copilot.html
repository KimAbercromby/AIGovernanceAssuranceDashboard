Using this dashboard with Power BI and Copilot

← Back to the dashboard

This dashboard is a blueprint for AI assurance reporting, not a replacement for a business intelligence platform. It sets out what a Board should see to answer “is AI governance working?”: the measures, the targets, and the rules for reading them. Most organisations already have the tools to run it for real. This page shows how to rebuild it in Power BI and how to use Microsoft Copilot alongside it.

How the three fit together

Defines

This dashboard

Fixes the eight assurance measures, their targets and the rules for reading them, so the Board sees the same thing, worked out the same way, every quarter. Use it to agree the content before anyone builds anything.

Runs

Power BI

Rebuilds the same view on your own data platform, refreshed on a schedule, with your access controls and sharing. The dashboard’s CSV files become tables fed from your source systems.

Explores

Copilot

Answers the follow-up questions (“why is the Housing edit rate up?”) and drafts the narrative for the Board paper. It works best when you give it the dashboard’s definitions, as in the prompts below.

Why not just ask Copilot?

Copilot is good at one-off questions and at drafting. On its own it does not know which measures make up AI assurance, what the targets are, or when a sample is too small to judge, and it can give a slightly different answer each time it is asked. Board assurance needs fixed definitions, so a trend means something from one quarter to the next and an auditor can check how each figure was produced. The dashboard supplies those definitions; Power BI applies them the same way every time; Copilot helps people understand the result.

Rebuild it in Power BI

1. One table per file

Each CSV file the dashboard loads becomes a table in Power BI. Keep the same column names: they are the agreed definitions, and the dashboard’s Template buttons give you the exact headers.

2. Carry the rules over exactly

These are the rules the dashboard applies. Written as Power BI calculated columns and measures, they give the same answers the dashboard does. Table names here match the files above; rename them to suit your model.

Is a measure on target? The scorecard says whether higher or lower is better for each measure.

On target =
IF (
    'Assurance KPIs'[better] = "lower",
    'Assurance KPIs'[value] <= 'Assurance KPIs'[target],
    'Assurance KPIs'[value] >= 'Assurance KPIs'[target]
)

Review status of each AI system. Overdue once the review date has passed; Due soon within 60 days.

Review status =
VAR DaysLeft = DATEDIFF ( TODAY (), 'AI register'[next_review], DAY )
RETURN
    SWITCH (
        TRUE (),
        ISBLANK ( 'AI register'[next_review] ), "No date",
        DaysLeft < 0, "Overdue",
        DaysLeft <= 60, "Due soon",
        "On track"
    )

Check the scorecard against the register. The dashboard recalculates three measures from the register and warns when the reported figure differs by more than one percentage point. In Power BI, the same three figures come straight from the register:

Reviews not overdue % =
DIVIDE (
    COUNTROWS ( FILTER ( 'AI register', 'AI register'[Review status] <> "Overdue" ) ),
    COUNTROWS ( 'AI register' )
) * 100

High-risk with signed-off DPIA % =
VAR HighRisk =
    FILTER ( 'AI register', 'AI register'[risk_tier] IN { "High", "Critical" } )
RETURN
    DIVIDE (
        COUNTROWS ( FILTER ( HighRisk, CONTAINSSTRING ( 'AI register'[dpia], "signed" ) ) ),
        COUNTROWS ( HighRisk )
    ) * 100

Suppliers with current evidence % =
DIVIDE (
    COUNTROWS ( FILTER ( 'AI register', CONTAINSSTRING ( 'AI register'[supplier_evidence], "current" ) ) ),
    COUNTROWS ( 'AI register' )
) * 100

Once the scorecard is calculated from the register like this, the figures cannot drift apart, which is better than checking them afterwards.

Edit rate tolerance. The tolerance line on the performance chart is the target of the edit_rate measure in the scorecard. Draw it as a constant line from that measure rather than typing a number into the chart.

Outcomes by group. Flag a group whose edit rate is 5 or more percentage points above the Overall row for the same period. Do not judge a group with fewer than 30 outputs reviewed: show it as “Small sample” instead.

3. Keep the Board view the same

  • Keep the one-line summary at the top: how many measures are off target, how many systems are overdue review, and the biggest performance risk.
  • Flag only a missed target in red. A change against the previous period is shown, not judged.
  • Keep the action log on the same page as the findings, so every red item has an owner and a date.

Use it with Copilot

Copilot gives consistent, checkable answers when you tell it the definitions. These prompts work on the dashboard’s files, or on the same tables in Excel or Power BI. In Excel, format each sheet as a table first.

Overdue reviews. “Using the AI register table, list every system whose next_review date is before today. Group them by service and show the owner and risk tier. Put High and Critical systems first.”
Missed targets. “In the assurance KPIs table, a measure is on target when value is at least target where better is ‘higher’, or at most target where better is ‘lower’. List the measures that are off target, with this period, the previous period and the target.”
Where the AI is least reliable. “In the edit rates table, find the team with the highest edit_rate in the latest period, and how it changed from the previous period. Compare it with a tolerance of [the edit_rate target from the scorecard]%.”
Fairness check. “In the fairness table, for the latest period, list any group whose edit_rate is 5 or more percentage points above the Overall row. Leave out groups with fewer than 30 outputs reviewed, and say which groups you left out.”
Board narrative. “Using only these tables, write a short summary for the AI Assurance Board: how many measures are off target, which systems are overdue review, the biggest performance risk, and which actions are late. Do not add figures that are not in the tables.”
Follow-up question. “The Housing edit rate rose this period. Using the incidents and edit rates tables, what else changed in the same period that might explain it? Say what the data cannot tell us.”
Before you use Copilot on real data. Use only your organisation’s approved Copilot, under its own data protection terms. Keep resident-level and special category data out of prompts: these tables are summaries for a reason. Treat Copilot’s answer as a draft. The figures that go to the Board come from the fixed definitions above, and someone accountable checks the narrative before it is circulated.

What stays with people

  • Agreeing the measures and targets, and changing them through governance rather than in a report.
  • Owning the source data, and its quality, for each table.
  • Deciding what a red result means and what action to take. A dashboard, Power BI report or Copilot answer informs that decision; it does not make it.
